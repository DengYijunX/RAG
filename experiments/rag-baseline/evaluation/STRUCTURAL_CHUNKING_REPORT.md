# 结构感知切片：修掉"条文被切开"的根因

日期：2026-10-10（Asia/Shanghai）。分支 `work`。前置：[CONTEXT_WIRING_REPORT.md](CONTEXT_WIRING_REPORT.md)（重排与扩展`）、[RETRIEVAL_MODES_REPORT.md](RETRIEVAL_MODES_REPORT.md)。

## 问题

4 道会计题在任何配置下都失败：ACC-Q041/Q059/Q073/Q083。归因一直是 `never_retrieved`，但**根因不在检索，而在切片**——目标条文横跨两个切片的接缝，因此没有任何单个可检索单元包含它。

以 ACC-Q041 为例（CAS-35-2006 第五条）：

| 切片 | 结尾 / 开头 |
| --- | --- |
| `:0000` | …考虑下列因素：**（一）各单项产品或劳务的性质，包括…** ← 第五条在此**被截断** |
| `:0001` | **（一）各单项产品或劳务的性质…**（重复）…（四）（五） |

源文件里第五条是**完整的一个 `###` 小节**（第 21–33 行，294 字），而它被切在中间。

## 根因

[rag/splitter.py](../../../rag/splitter.py) 用 `RecursiveCharacterTextSplitter`，分隔符是**通用的**：

```
["\n\n", "\n", "。", ".", "？", "?", " ", ""]
```

条文边界（`###`）**不在其中**。分割器把 500 字尽量打包，打满时按 `\n\n` 断开——于是断点落在条文内部。

而 [rag/structure.py](../../../rag/structure.py) **一直都能识别**这些边界：`第五条` 被解析为 level=3、跨度 `298-616` 的独立结构单元，`###` 条文 45 个全部识别。**结构算出来了，却只用于记录，没用于切片。**

## 改动

新增 [rag/structural_split.py](../../../rag/structural_split.py)，按一个原则工作：**先试文档自己声明的边界，再用通用分隔符**。

```
[ r'(?=\n#{1,6}[ \t])',   ← 任何 ATX 标题
  '\n\n', '\n', '。', '.', '？', '?', ';', '；', ' ', '' ]
```

`RecursiveCharacterTextSplitter` 按顺序使用分隔符，因此标题会成为**先于**空行与句号的候选边界；而超长的小节仍会在自身内部被细分。

**这是通用的，不是领域规则。** 它只依赖文档自身的标题结构——markdown 标题、PDF 分节、纯文本显式分节都算，**没有任何规则提到中文法条或具体准则**。没有标题的文档自动退回原行为。

### 一个踩过的坑

第一版分隔符写成 `(?=^#{1,6}[ \t])`，**看起来对但完全没生效**——`^` 让分割器把每个行首都当成边界，产出与通用切片完全相同的切片。必须用 `(?=\n#{1,6}[ \t])` **锚定在换行上**。这个坑写进了代码注释。

## 决策

**结构切片设为默认（切片大小仍为 500）。**

理由：会计上全面改善（recall +3.7pp、ndcg +4.5pp、首命中槽位 1.365→1.188），**售后逐位不变**（那 5 个 FAQ 文档没有标题，自动退回通用切片）。默认值只改一个维度，且风险已被测量为零。

**切片大小不改默认。** 1000 字在会计上更好且能修复全部 4 题，但在售后上**略降**（recall 0.9762→0.9714、ndcg 0.8947→0.8831）——这是"切片更粗"的真实代价，属于需要权衡的改动，不由我单方面改默认。想用可以设 `CHUNK_SIZE=1000`。

## 必须说明的影响

1. **换了默认切片方式后，所有已发布索引与既有检索数字都失效**，需要重新导入并重跑基线。本轮只对新建索引做了对照测量，**旧的基线产物仍是通用切片的结果**，报告里已标注。
2. 结构切片的片数更多（会计 749→866），平均片更短（中位 463→399 字）——这对嵌入调用量有影响（+15.6% 片段）。
3. **未做生成侧验证**。本轮只测了检索指标与"条文是否完整落片"。按此前经验，检索指标改善不自动等于答案改善（邻段扩展就是反例），所以生成侧需要复测才能宣称端到端收益。
4. 仅在两个语料上验证；第三语料（`test_docs/third-corpus`）未测。
